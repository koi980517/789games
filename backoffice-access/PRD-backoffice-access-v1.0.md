## 1. 背景与范围

### 1.1 条款原文

> **Back-office access**：Each GSA must use a single back office with one URL. Both PAGCOR and megaXcess must be able to always access the back office. PAGCOR must be notified of any changes to the back office or its access details.
>
> 每个 GSA 必须使用一个后台系统，并采用统一的访问网址。PAGCOR 和 megaXcess 必须能够随时访问该后台。后台系统或访问方式如有变更，须通知 PAGCOR。

拆成三条要求：

| # | 要求 | 产品含义 |
|---|---|---|
| R1 | 一个 GSA 只用**一个**后台、**一个** URL | 同一 GSA 下的所有品牌（789games、789bingo 如同属一个 GSA）在同一后台、同一域名内管理，用「站点切换」区分；不再对外存在第二个管理入口 |
| R2 | PAGCOR、megaXcess **随时**能访问 | 给两方开固定的监管账号；访问不被 IP 白名单、FIDO2 USB 钥匙、账号过期 / 锁定、后台精简删菜单等内部措施挡住；后台可用性要监控 |
| R3 | 后台或访问方式变更须**通知 PAGCOR** | 变更先登记、通知 PAGCOR 留回执，再生效；系统里涉及访问方式的配置改动，没有已通知记录时不允许生效 |

### 1.3 包含 / 不包含

| 包含 | 不包含 |
|---|---|
| 统一后台入口：一个 URL + 登录后站点切换 | 合并两站的业务数据库 |
| 其他管理入口收口（重定向 / 下线 / 限内网），清单待运维给 | 代理后台的业务功能改造 |
| 监管账号（PAGCOR、megaXcess）：只读角色、专用登录方式、防误改保护 | 给监管方开写权限 |
| 访问变更登记：登记 → 合规审核 → 通知 PAGCOR → 生效，含系统拦截 | 自动发邮件给 PAGCOR（v1 人工发送，系统留痕） |
| 监管访问监控：可用性探测、监管账号登录 / 访问日志、异常告警 | 监管方提出的新报表（另立需求） |

### 1.4 目标

1. 对外只有一个后台 URL，审计抽查时 PAGCOR / megaXcess 用监管账号 1 次登录即可看到所有站点数据。
2. 监管账号任何时候可登录：月可用率 ≥ 99.9%（待确认），登录失败 5 分钟内告警。
3. 所有访问方式变更 100% 有登记和 PAGCOR 通知回执，未通知的变更系统内不能生效。

### 1.5 适用范围

- 站点：789games、789bingo（前提：两站属于同一 GSA，见待确认 Q1）
- 端：后台（PC Web）；前台 H5 / App 不改
- 时区：GMT+8；语言：后台中文 + 监管账号界面 English

## 2. 规则

| 项目 | 规则 |
|---|---|
| 唯一入口 | 生产后台只保留一个域名（下称「主后台 URL」，具体值待确认 Q2）。其他管理入口：能并入的并入；不能并入的（如 third-manage）改内网访问或下线；旧域名 301 到主后台 URL 并保留 ≥ 90 天 |
| 站点切换 | 登录后顶栏显示「当前站点」下拉：全部 / 789games / 789bingo。员工按已授权站点可切；监管账号默认「全部」且可切任一站点 |
| 代理后台 | 是否算「另一个后台」待确认 Q3。默认方案：代理后台挂在主后台 URL 的子路径（/agent），登录页统一 |
| 监管账号 | 每个监管方 ≥ 2 个具名账号（PAGCOR、megaXcess 各自提供人员）；角色固定为「监管只读」；不能被普通管理员禁用、删除、降权，只有「合规管理员」可操作且须走访问变更登记 |
| 监管账号登录 | 账号 + 密码 + Google Authenticator（TOTP）；不要求 FIDO2 USB 钥匙；不受员工 IP 白名单限制（或预登记监管方 IP，见 Q5）；密码不强制定期过期；连续失败锁定 30 分钟后自动解锁，并告警合规管理员 |
| 监管只读范围 | 全部菜单可见可查询、可导出；所有新增 / 编辑 / 删除 / 审核 / 派奖按钮隐藏且服务端拒绝；敏感字段（手机号、证件号、银行卡）按监管要求明文或脱敏，待确认 Q6 |
| 菜单下线 | 后台精简删除菜单前，需确认不影响监管只读范围；影响 PAGCOR 报表的菜单变更视为「访问变更」 |
| 变更通知 | 以下变更须先登记并通知 PAGCOR：① 后台 URL / 域名 / 证书主体；② 登录方式（2FA 类型、SSO）；③ IP 访问策略；④ 监管账号新增 / 停用 / 权限调整；⑤ 菜单 / 报表新增、下线、口径变更（监管只读范围内）；⑥ 计划内停机维护；⑦ 后台系统更换 / 机房迁移 |
| 通知时限 | 计划内变更：生效前 ≥ N 个工作日通知（N 待确认 Q7，默认 7）；紧急变更（安全事件）：生效后 24 小时内补通知 |
| 系统拦截 | 类型 ①③④ 对应的系统配置（域名配置、IP 策略、监管账号）保存时，必须选择一条状态为「已通知 PAGCOR」的变更单，否则不能保存 |

## 3. 页面与流程

```
[发起人] 新建变更单 → [合规管理员] 审核 → 线下发 PAGCOR（邮件 / 公函）→ 上传通知回执 → 状态=已通知
      → 到生效时间 → [运维/后端] 执行，系统配置保存时关联该变更单 → 状态=已生效 → 通知 megaXcess（抄送）
驳回 → 发起人修改后重提；取消 → 已通知的需补发取消通知
```

| 编号 | 页面 | 触发 | 表现 |
|---|---|---|---|
| A1 | 统一登录页 | 访问主后台 URL / 旧域名 301 跳转 | 一个登录框；登录方式按账号类型：员工 = 密码 + FIDO2；代理 = 密码 + Google；监管 = 密码 + Google |
| A2 | 顶栏站点切换 | 登录后 | 「当前站点」下拉；监管账号顶栏显示「监管只读 · PAGCOR / megaXcess」标签 |
| A3 | 系统管理 › 监管账号 | 合规管理员 | 列表 + 新增 / 停用（须关联变更单）、重置 2FA、查看访问日志 |
| A4 | 系统管理 › 访问变更登记 | 运维 / 后端 / 合规 | 列表 + 新建 + 详情（状态流、回执、关联的系统配置改动） |
| A5 | 系统管理 › 监管访问监控 | 合规 / 运维 | 可用性探测结果、监管账号最近登录、失败告警、访问日志 |
| A6 | 监管只读视图 | 监管账号登录 | 同员工后台菜单，所有写操作按钮隐藏 |

## 5. 后台配置

菜单：系统管理（新增）› 监管账号 / 访问变更登记 / 监管访问监控。

### 5.1 监管账号（A3）

列表列：账号、所属监管方（PAGCOR / megaXcess）、姓名、邮箱、2FA 状态、状态（启用 / 停用 / 锁定）、最近登录（GMT+8）、创建时间、关联变更单、操作。

新增表单：

| 字段 | 必填 | 规则 |
|---|---|---|
| 监管方 | 是 | PAGCOR / megaXcess |
| 姓名、邮箱 | 是 | 邮箱用于接收 2FA 绑定链接 |
| 账号 | 是 | 系统生成：`pagcor_姓名缩写` / `mx_姓名缩写`，可改，唯一 |
| 站点范围 | 是 | 固定「全部站点」，不可改 |
| 角色 | 是 | 固定「监管只读」，不可改 |
| 允许 IP | 否 | 默认不限；填了则仅这些 IP 可登录（见 Q5） |
| 关联变更单 | 是 | 只能选状态 = 已通知 PAGCOR、类型含「监管账号」的变更单 |

保护：停用 / 删除 / 改 IP 需二次确认 + 关联变更单；删除只做软删除；最后一个启用的 PAGCOR 或 megaXcess 账号不允许停用。

### 5.2 访问变更登记（A4）

列表筛选：变更类型、状态、计划生效时间、发起人。列：单号（AC-YYYYMMDD-序号）、标题、类型、影响站点、计划生效时间、通知时间、状态、发起人、操作。

新建表单：

| 分组 | 字段 | 必填 | 规则 |
|---|---|---|---|
| 基础 | 标题 | 是 | ≤ 60 字 |
| 基础 | 变更类型 | 是 | 多选：①–⑦（见第 2 节） |
| 基础 | 影响站点 | 是 | 789games / 789bingo / 全部 |
| 内容 | 变更前 / 变更后 | 是 | 文本，域名、IP、登录方式写具体值 |
| 内容 | 计划生效时间 | 是 | GMT+8，精确到分；早于「现在 + N 个工作日」时须勾选「紧急变更」并填原因 |
| 内容 | 对监管访问的影响 | 是 | 无影响 / 短暂中断（填时长）/ 访问方式改变（填新方式） |
| 通知 | 通知 PAGCOR 方式 | 合规审核时 | 邮件 / 公函 / 门户；通知时间；回执附件（pdf / png / jpg，≤ 10MB） |
| 通知 | 抄送 megaXcess | 否 | 默认勾选 |

状态：草稿 → 待合规审核 → 待通知 → 已通知 PAGCOR → 已生效；分支：已驳回、已取消。

| 状态 | 谁操作 | 能否被系统配置关联 |
|---|---|---|
| 草稿 / 待合规审核 / 待通知 | 发起人 / 合规 | 否 |
| 已通知 PAGCOR | 合规上传回执后 | 是 |
| 已生效 | 关联的配置保存成功后自动置为已生效（可多条配置关联同一单） | 是（生效后 7 天内） |
| 已驳回 / 已取消 | 合规 | 否 |

### 5.3 监管访问监控（A5）

- 可用性探测：每 1 分钟从外网探测主后台 URL 登录页（HTTP 200 + 证书有效），连续 3 次失败告警（Telegram 运维群 + 合规，通道待确认 Q8）。
- 监管账号健康：每天 09:00（GMT+8）检查每个监管账号状态（启用、未锁定、2FA 已绑定、未过期），异常告警。
- 访问日志：监管账号的登录、登出、菜单访问、查询条件、导出，保留 ≥ 1 年（Q9）。
- 页面：顶部 4 个卡片（近 30 天可用率、当前状态、监管账号正常数 / 总数、未处理告警），下方探测记录表与访问日志表。

## 10. 验收要点

1. 旧后台域名、代理后台旧入口访问均 301 到主后台 URL；third-manage 外网不可达。
2. 监管账号登录不要求 FIDO2；员工账号仍要求。
3. 监管账号在员工 IP 白名单外可登录（或仅预登记 IP 可登录，按 Q5 结论）。
4. 监管账号调用任一写接口（直接发请求）返回无权限，并记日志。
5. 站点切换：监管账号选「全部」能看到两站数据，切单站数据只含该站。
6. 不关联变更单 / 关联未通知的变更单时，保存域名配置、IP 策略、监管账号均被拒绝。
7. 最后一个启用的 PAGCOR 账号不能停用。
8. 连续 3 次探测失败产生告警；监管账号被锁定产生告警。
9. 跨 00:00（GMT+8）的访问日志归日正确；变更单计划生效时间按工作日计算 N 天。

## 12. 风险与依赖

| 等级 | 类别 | 风险 | 应对 |
|---|---|---|---|
| 高 | 合规 | 789dropball.com 改二级域名若先于本需求上线，属于未通知的访问变更 | 运维改域名前先登记变更单并通知 PAGCOR |
